# IPv6 优选方案（v1.6.7 候选）

> 状态：**只有方案，未动代码**（2026-11-18 重写）。
> 旧版方案方向写错，已备份到 `.scratch/IPv6方案-old-20261118.md`。
> 一句话：**IPv6 要和 IPv4 走同一条路——从 Cloudflare 的 IPv6 段里优选节点，写进 AdGuard Home 和 DDNS，目标仍是"加速访问 Cloudflare"，不是"让外网访问你家 NAS"。**

---

## 零、方向纠正记录（先读这段）

2026-11-17 的旧方案把"支持 IPv6"理解成：**测速链路不动，另把 NAS 自己的公网 IPv6 写进 AAAA，让外网能访问家**。2026-11-18 用户指出方向不对，代码核实结论：

| 事实 | 证据 |
|---|---|
| 写进域名 A 记录的 IP | `pushIPs` ← `res.IPs`，是**测速筛出的 Cloudflare 节点**，不是家 NAS 的地址（`web/server.go:1323,1337`） |
| 写进 AdGuard 重写的 IP | `best = res.IPs[0]`，同样是 **CF 节点**（`web/server.go:1266,1299`） |
| 这个产品的主线 | 从 CF 地址里挑最快 → 写 AdGuard + DDNS。全程不涉及"家的地址" |

**所以本方案的方向**：照抄 IPv4 那条链路，只把"IPv4 节点"换成"IPv6 节点"。旧方案写的"读本机网卡 / 写家地址"那套（阶段①已做的 `ipv6/` 只读显示）**不再是主线**，但作为"这台机器有没有 v6 出口"的前置探测仍有价值（见第九节）。

## 一、名词

| 名词 | 人话 |
|---|---|
| A / AAAA 记录 | A 装 IPv4 地址，AAAA 装 IPv6 地址。同一域名可两条都有，客户端按自己支持哪套选。 |
| CF 节点 / 优选 IP | Cloudflare 在全球的入口地址。你家连哪个最快因网络而异，"优选"就是测出来。CF 公布的 IPv4 段有 15 条、IPv6 段只有 **1 条**（`2606:4700::/32`）。 |
| 节点串 | 测速引擎内部表示一条候选的格式，现在是 `1.2.3.4:443#US`（IP:端口#国家）。IPv6 需要写成 `[2606:4700::1]:443#US`（方括号不能省，否则地址里的冒号和端口的冒号分不清）。 |
| 反代验证 | 引擎最有价值的一步：光 TCP 能连不算数，还得假装访问一个 CF 域名、确认真的能承载 HTTPS 请求。这是"优选结果靠谱"的保证。 |
| 双栈 / ipv6_only | 一次请求的出口可能是 v4 或 v6。现在引擎默认开 `FILTER_IPV6_AVAILABILITY`，会把"出口只有 IPv6"的节点剔掉——**做 v6 优选后这条语义要重新定**（见第七节）。 |

## 二、做出来之后是什么样

**界面**：沿用现有「优选 IP 段」输入框，允许填 IPv6 段/地址；测速结果里能列出 v6 节点（地址、速度、延迟）。「记录类型」下拉加 `AAAA`，选了之后 DDNS 写 AAAA、AdGuard 重写照写（答案本来就是字符串，原生支持 v6）。

**数据链路**（两条并列，互不干扰）：

```
内置/自定义 CF 段（v4 + v6）→ 采样出候选节点 → TCP 延迟 → 反代验证 → 带宽测速
                                                       ├→ 最优 v4 → AdGuard 重写（域名 → v4）
                                                       └→ 按类型写 DDNS：A 写 v4 / AAAA 写 v6
```

注意：**v4 和 v6 的"最优"是分别评的**——同一条 v6 地址对国内的速度可能远好于 v4（也可能是反过来），所以两条路独立选、独立写。

## 三、关键技术点：v6 候选从哪来

Cloudflare 官方公布的 IPv6 段只有一条 `2606:4700::/32`（项目里 `web/cfcheck.go:62` 已记录，校验域名是否走 CF 时也用它）。

**难点**：IPv4 那套采样代码（`web/candidates.go:131-208`）是 32 位专用的——`cidrEntry.base uint32`、`binary.BigEndian.Uint32`、`rand.Uint32()%size`、`seen map[uint32]bool`。`/32` 的 v6 段有 **96 个主机位**，`uint32(1)<<96` 在 Go 里直接溢出成 0，**完全不能复用**。必须新写基于 `net/netip.Addr`（128 位）的采样。

但有个现实约束：**`/32` 太大了**。它覆盖 2^96 个地址，随机撒 600 个点几乎不可能撞到同一台边缘设备——这既是好事（覆盖广）也是坏事：v6 是 Anycast，同一个 /64 里的地址很可能走同一条路，撒得再广也可能测出差不多的延迟。**v6 优选的实际收益必须实测才能定论**，方案第一阶段就是回答这个问题（见第九节）。

## 五、三处最容易出事故的地方

### 1. 清理逻辑绝不能跨类型删记录
写 AAAA 只删 AAAA，写 A 只删 A。删错会导致用户正在用的解析**安静地断掉**。必须给四家各写一条"写 AAAA 不动 A / 写 A 不动 AAAA"的测试。

### 2. 静默的解析错误
`parseOutput` 对裸 v6 串会把端口并进地址、`looksLikeIP` 放行畸形串——这类错误不报错，只是结果悄悄错了。必须统一"v6 节点串一律带方括号"的格式约定，并在 Go 端用 `netip.ParseAddr` 兜底校验。

### 3. `FILTER_IPV6_AVAILABILITY` 的语义冲突
它现在默认 `true`，会剔除出口为 `ipv6_only` 的节点。做 v6 优选后，这个开关到底该过滤什么要想清楚：
- 若目标是"双栈都能用" → 保留过滤，但那等于不要纯 v6 节点，与 v6 优选矛盾；
- 若目标是"v6 也能优选" → 需改成按记录类型决定过滤策略，或默认关掉。

**已定（2026-11-18 用户拍板）：写 AAAA 时关掉它**，让 v6 节点真正能入选。
注意阶段①（探测）不写任何解析，所以这一条**到阶段②才落地**；阶段①只观察到"过滤开关开着"时 v6 节点会不会被提前剔掉——
若会，阶段①就在引擎配置里显式关掉它（通过 `writeCfnbConfig` 的 overrides，不改 schema 默认值）。

## 八、收益预期（先说清楚，免得白做）

- CF 的 v4 有 15 个段可撒开测，v6 只有 `/32` 一段；v6 是 Anycast，同一 /64 里地址很可能走同一路径。
- **"从 CF v6 里选出明显更快的节点"这件事是否成立，目前没有证据**。国内家宽走 v6 到 CF 的质量可能好于、等于、或差于 v4，因运营商而异。
- 已知真机事实（阶段①截图）：这条宽带**确有公网 v6**（电信 `240e:341:…`，/64，网卡 eno1-ovs）——这是做 v6 优选的前提，已具备。
- 所以方案分两阶段：**先做"探测/显示"，用真机数据证明 v6 优选有价值，再决定是否写入**（见第九节）——避免投入大量改造后才发现没意义。

## 九、分阶段（先探测、后写入）

| 阶段 | 内容 | 风险 | 价值 |
|---|---|---|---|
| **① 探测（先做）** | 改引擎的解析+采样+连接（第四节 A/B/C），但**不写入 DDNS/AdGuard**，只在后台显示"v6 候选列表 + 各自延迟/速度 + 与 v4 最优的对比"。阶段①已有的只读卡片保留 | 中（动引擎，但不改线上解析） | 用真机数据回答"v6 优选到底有没有更快节点"——决定后面值不值得做 |
| **② 写入** | 四家 DDNS 支持 AAAA、按类型分流、清理不跨类型；AdGuard 重写写 v6 | 中（会让线上解析变化） | 主功能：域名走优选 v6 |
| **③ 稳定化** | `FILTER_IPV6_AVAILABILITY` 语义定稿、前缀变化巡检（可选）、日志与提示补全 | 低 | 让整套东西长期可用 |

**阶段①是可逆的**：只改测速引擎、不写任何解析/AdGuard，出问题回退一版即可。

## 十、验收标准

**阶段①**
1. 后台能列出 CF v6 候选节点（带方括号格式正确解析、不被 `looksLikeIP` 误收）；
2. 反代验证对 v6 节点能通过（resolver 的 `AF_INET6` 改对了）；
3. 日志里能看到 v6 节点的数量、延迟、带宽，以及和 v4 最优的对比；
4. v4 原有测速结果不退化（回归测试）。

**阶段②**
1. `dig AAAA 域名` 返回优选出的 CF v6 地址；
2. `dig A 域名` 的原记录**一条没少**（最易翻车处）；
3. 把「同步几条 IP」从 3 改 5 再保存，不影响另一类型。
