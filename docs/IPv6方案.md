# IPv6 方案（v1.5.x 候选）

> 状态：**只是方案，没有动任何代码**（2026-11-17 你选的「先写方案文档」）。
> 用途：等你决定做的时候，照这份文档执行，不用再重新勘探一遍。
> 一句话：**这份文档要解决的不是「让加速更厉害」，而是「多一种把域名指到某处的方式」。**

---

## 一、先把名词说清楚

用户不需要懂这些，但方案里要反复用到，所以先定死。

| 名词 | 人话 |
|---|---|
| IPv4 / IPv6 | 两套并列的地址体系。你家的宽带**同时**有这两种地址。IPv4 地址像 `1.2.3.4`，IPv6 像 `2408:8207:1234:5678:abcd:ef01:2345:6789` |
| A 记录 / AAAA 记录 | 域名解析里的两条不同记录：**A 记录装 IPv4 地址，AAAA 记录装 IPv6 地址**。同一个域名可以两条都有，客户端按自己支持哪套去选 |
| 优选 IP | Cloudflare 在全球有很多入口，从你家连过去延迟差别很大。「优选 IP」就是测出**你家最快的那几个入口地址**——注意，这套东西是 **IPv4** 生态 |
| 公网 IPv6 | 运营商直接分给你家的一段地址，外面能连进来。**这是本方案的核心** |
| 前缀 | 公网 IPv6 是「一段」而不是「一个」。运营商换一次前缀，你家里所有设备地址的前半截全变 |
| 临时地址（privacy extension） | 系统为了隐私，会再生成一些**每隔几小时就换一次**的地址。这种地址**绝对不能拿去写解析记录**，否则域名每小时失效一次 |

## 二、结论：只有一件事值得做

「支持 IPv6」在这套软件里是两件完全不同的事，代价差一个量级：

| | 内容 | 判断 |
|---|---|---|
| **A. 让优选 IP 走 IPv6** | 测速引擎去测 Cloudflare 的 IPv6 节点，把 v6 地址写进重写/解析 | **不做。** ① Cloudflare 的「优选 IP」生态本身就是 v4 的；② 家用宽带走 v6 到 CF 的质量通常还不如 v4；③ 这要动测速引擎 `third_party/cfnb/main.py`——那是项目红线（「只许改注入配置」） |
| **B. 把家里的公网 IPv6 写进域名的 AAAA 记录** | NAS 有公网 v6，想让某个域名指向它 | **做这个。** 这才是「我有公网 IPv6」的实际用法 |

**本方案只覆盖 B。**

## 三、做出来之后，你在界面上会看到什么

「域名解析」那张卡片里多两样东西：

```
记录类型     [ A（优选 IP）  ▾ ]      ← 新增，默认还是 A，老用户升级后看不到任何变化
                                      ↓ 只有选了「AAAA（本机 IPv6）」才出现下面这几项
IPv6 地址来源  [ 自动读取本机  ▾ ]    ← 或者选「手动填写」
当前本机 IPv6  2408:8207:xxxx:xxxx:....:1  （来自 enp1s0，稳定地址）
              ⚠ 这条地址能不能从外网访问，取决于你路由器放不放行
```

选 `A` 的时候，界面和现在**一模一样**（「同步几条 IP」照旧）。选 `AAAA` 时「同步几条 IP」会隐藏——**家里通常只有一个地址，写多条没有意义**。

## 四、数据从哪来 → 经过哪几步 → 到哪去

现在（v1.4.1）的链路，与 IPv6 完全无关：

```
测速（Cloudflare v4） → 最优 IP → ①写 AdGuard 重写 → ②写域名 A 记录
```

做完 B 之后，是**两条并列的路**，互不干扰：

```
测速（Cloudflare v4） → 最优 IP → 写 AdGuard 重写（不变）
                              → 写域名 A 记录（不变，类型可配）

本机网卡 → 挑出「稳定的公网 IPv6」→ 写域名 AAAA 记录（新增）
                              → （可选）写 AdGuard 重写，答案填这个 v6
```

**为什么必须是两条路，而不是"复用测速结果"**：测速结果是 Cloudflare 的入口地址，指向的是 Cloudflare 的机房；家里的 v6 地址指向的是你家 NAS。两者地址不同、更新节奏也不同（前缀随时可能变）。

## 五、关键技术点：「本机公网 IPv6」怎么取

这是整个方案里唯一需要真正设计的部分。三种可能做法：

| 做法 | 说明 | 判断 |
|---|---|---|
| **① 读本机网卡** | 容器是 `network_mode: host`，和 NAS 共用网络栈，所以**能直接看到 NAS 上所有地址**。读 `/proc/net/if_inet6` 即可，不需要任何新依赖、不发外部请求 | **首选** |
| ② 问外部服务 | 例如向 `https://api6.ipify.org` 发请求问「你看到我是谁」 | **只做交叉校验**。你机器上代理是全局的，容易问出代理的地址；要强制直连 + 强制 v6 才准 |
| ③ 让用户手填 | 界面上给个输入框 | **作为兜底保留**（自动读不到时还能用） |

做法 ① 的具体判据（挑地址的规则）：

1. 只保留**全局**地址：排除 `::1`（本机回环）、`fe80::/10`（链路本地，外面连不到）、`fc00::/7`（内网私有段）；
2. **必须排除临时地址和未完成检测的地址**：`/proc/net/if_inet6` 每行带一个 flags 十六进制位，`0x01` 是临时地址（privacy extension）、`0x20` 是已废弃、`0x40` 是重复地址检测还没做完 —— 这三种都不能用；
3. 有多条合格地址时，挑**前缀长度 64、名字最短的那块网卡**（家里的主网卡），并在日志里把「挑了哪条、为什么」写清楚。

> **实现时必须先做的一步**：在一台真机上把 `cat /proc/net/if_inet6` 和 `ip -6 addr`（带 `temporary` 标记的那个）对照一遍，确认 flags 那一位的含义和你机器上的实际情况对得上。Linux 的 flags 定义（`include/uapi/linux/if_addr.h`）里 `IFA_F_TEMPORARY` 与 `IFA_F_SECONDARY` 共用 `0x01`，不同发行版/内核打印出来可能不一样——**不要凭记忆写死，要对着真机验**。

**并发/顺序**：读地址和写解析必须分开。读地址很便宜（读一个 proc 文件），可以每分钟做一次；写解析要走网络，只在「地址真的变了」时才做。否则每 60 分钟一次的测速周期根本跟不上前缀变化的节奏。

## 七、三处最容易出事故的地方

### 1. 清理逻辑绝不能跨类型删记录

现在的 `EnsureARecords` 语义是「对齐」：把域名下**多余的 A 记录删掉**，只留期望的那几条。加了类型之后：

- 写 AAAA 时，**只能删域名下的 AAAA 记录，一条 A 都不能碰**；
- 写 A 时同理，不能碰 AAAA。

代码里现有实现是 `rec.Type == "A"` 过滤（`cloudflare.go:142` 等），只要把那个字面量换成变量就天然安全。**但必须为这一条单独写测试**——一旦删错，用户正在用的解析会当场断掉，而且是"安静地断"。

### 2. 双栈时 IPv6 失败比 IPv4 失败更难受

客户端（手机、电脑）会**优先走 IPv6**。如果 v6 地址写进去了但外面连不通（路由器没放行、运营商封了端口），表现是「**有些设备能打开、有些打不开，而且特别慢**」——比完全不通更难排查。

所以方案里必须包含：
- 写进解析之前，先做一次「这条地址真的能从外面连上吗」的**自检**（最简单的做法：用这个 v6 地址回连自己的后台端口，能连上才算数；连不上就在日志里警告，但仍然照写——因为用户可能本来就想让内网设备用它）；
- 后台给一句人话提示：「如果你从手机流量打不开，说明路由器没放行这个端口的入站，去路由器里放行」。

### 3. Cloudflare 的橙色云朵会把 AAAA 也代理掉

如果这个域名在 Cloudflare 上并且开了橙云，AAAA 记录同样会被 Cloudflare 代理——**那就不指向你家了**。我们现在的 `Proxied` 默认是关的，正好合适。界面上选了 AAAA 且开了云朵时，必须给一句提示。

## 八、兼容性

- 老配置文件里没有新字段 → 反序列化后是零值 → **记录类型按 `A` 处理，行为与 v1.4.1 完全一致**。这条是这个项目一直在守的规矩（v1.3.0 加 TTL/云朵/条数时也是这么做的）。
- 备份/恢复的四个文件格式不变（字段是可选的）。
- 不新增任何依赖：读 `/proc/net/if_inet6` 用标准库 `os.ReadFile` 就够，不需要第三方包。

## 九、分四个阶段，第一阶段零风险

| 阶段 | 内容 | 风险 | 价值 |
|---|---|---|---|
| **① 只读** | 读本机 v6 并在后台**显示**（不写任何记录），列出所有候选 + 挑中的那条 + 为什么 | **零**（不碰解析、不碰 AdGuard） | **立刻回答「我这台机器到底有没有可用的 v6」**。没有的话，后面全不用做 |
| ② 写 AAAA | 四家服务商支持类型、配置、界面、清理逻辑不跨类型 | 中（会让线上解析变化） | 主功能 |
| ③ AdGuard 也能写 v6 | 多写一条重写（同域名、答案换成 v6），代码天然支持 | 低 | 局域网设备也能拿到家里 v6 |
| ④ 前缀变化即更新 | 每分钟读一次地址，变了才推；日志记一行「前缀变了，已更新」 | 低 | 让整套东西**真的能用**（不然重拨一次就失效） |

**强烈建议先只做 ①。** 它的成本最低、风险为零，而它要回答的那个问题（「我家到底有没有能用的公网 v6」）决定了后面三个阶段的全部价值。很多家宽的「有 IPv6」只是**你自己能用 v6 上网**（出站），别人连不进来（入站被防火墙挡），这两件事差别极大。

## 十、验收标准（做成什么样算成）

**阶段 ①**
1. 后台能显示「本机候选 IPv6」列表和「挑中的那条」；
2. 列表里**不出现** `fe80::` 开头的、`fc`/`fd` 开头的、以及带 `temporary` 标记的地址；
3. 把列表截图发我，我能据此判断哪条是稳定地址、前缀是多少位。

**阶段 ②**
1. `dig AAAA 你的域名` 返回的就是家里那条地址；
2. 家里原来在用的 A 记录**一条都没少**（这是最容易翻车的地方）；
3. 把「同步几条 IP」从 3 改成 5 再保存，AAAA 不受影响。

**阶段 ④**
1. 重启路由器换一次前缀，5 分钟内 `dig AAAA` 跟上（现在测速周期是 60 分钟，跟不上，所以必须独立巡检）；
2. 从手机流量（关 Wi-Fi）能打开 `http://[你家v6]:端口/`。

## 十一、明确不做的事

- ❌ 不做 Cloudflare 优选 IPv6（理由见第二节）
- ❌ 不做 NAT66 / 内网穿透 / 端口映射（那是路由器的事，不是这个软件的职责）
- ❌ 不碰测速引擎 `third_party/cfnb/main.py`
- ❌ 不为了 IPv6 修改容器网络模式（已经是 host，够用）
- ❌ 不做「自动帮你开路由器防火墙」（做不到，也不该做）

---

## 十二、做之前需要你回答的三个问题

1. **你想让哪个域名指向家里？** 是现在这个专门做加速的域名，还是另一个（比如 `home.xxx.com`）？——建议**用另一个**，别和「加速域名」混在一起，混了以后两边互相覆盖，排查起来很痛苦。
2. **你家路由器放行入站了吗？** 如果没放行，阶段 ① 做完就能看出来（地址有、但外面连不进来）。
3. **要指向的端口是多少？** 家宽运营商经常封 80/443，如果只是 NAS 后台，用高位端口更稳。
