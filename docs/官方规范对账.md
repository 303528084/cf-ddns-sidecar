# 飞牛官方规范对账

> 依据：`developer.fnnas.com` 官方文档（2026-11-17 通读《应用框架》《环境变量》《应用权限》《Manifest》《应用资源》《Docker 应用案例》六页）。
> 对象：本项目 `fpk/template/` 下全部内容（manifest、config/privilege、config/resource、cmd/ 九个脚本、app/docker/docker-compose.yaml、app/ui/config、wizard/）。
> 性质：**只做对账，不改代码**。每条都写了「官方怎么说 / 我们怎么做 / 判定 / 建议 / 代价」。

## 一、结论摘要（先看这一页）

**符合 11 条，偏离 6 条，不符 5 条，待真机实测 3 条。**

四条最重要的：

1. **数据落点应当用平台给的目录，不该自造。** 官方在《应用框架》里写明：安装后 `/var/apps/<appname>/` 下由平台自动建好 `var → /vol{n}/@appdata/<appname>` 等五条软链，配套环境变量是 `TRIM_PKGVAR`。我们 v1.3.2～v1.4.1 却自己在 `/vol1` 根目录下建 `<app>-data` / `<app>-backup`，再反过来把 `/var/apps/` 下的路径做成软链指向它。**这不是「搬得不够远」，而是绕开官方机制另造一套**——所以它失败得那么彻底（`package` 用户建不动 root 的目录），而且每一版的日志都看不见。
2. **`run-as: root` 是官方支持的，且官方点名的适用场景正是我们这种情况。** 原文：「只有生命周期脚本确实需要执行特权准备任务时，才使用 Root 模式……长期运行并对外提供访问的进程，应尽可能以非 root 用户运行。」我们的容器本来就自己 `su-exec app`，外面那层脚本要的只是 `mkdir` / `chown`。
3. **共享目录（`data-share`）的定位是「给用户在文件管理器里看的文件」，不是应用自己的运行数据。** 官方原文：「不要将内部工具或内部数据目录作为共享资源暴露。」我们从 v1.1.0 起把含密钥的 `config.json`、`ddns.env` 放在 `share/<app>/data` 里，方向就不对。
4. **「静默失败」是明确违规。** 官方在《应用框架》里专门有一节《用户可见错误》：脚本失败前应把清楚的错误写进 `TRIM_TEMP_LOGFILE`。我们恰好相反——`upgrade_init` 里大量 `2>/dev/null`，`install_callback` 用 `|| true` 兜住一切。

## 三、必须真机实测的三件事（决定 v1.5.0 怎么写）

这三条**文档里查不到答案**，只能装一次看结果。前两条不成立，v1.5.0 的方案就得改。

1. **`${TRIM_PKGVAR}` 在 Docker 类应用的 compose 里到底会不会被替换？**
   官方只在《Docker 应用案例》的「常用变量」列表里点了名，没有给 docker 项目的实例；而 wizard 变量恰恰也是这么被「顺带」支持的，说明这类替换是真实存在的机制。→ 验证方式：把它挂上去，装完看容器里 `/app/data` 是不是空的挂载点（`df` 或日志里打印路径）。
2. **`/vol{n}/@appdata/<app>` 的属主和 ACL 是否允许容器里的 uid 1000 写？**
   官方说共享目录用 Windows ACL 模型、「系统会自动为应用运行用户授予所需的 ACL」，但没说 `@appdata` 是否同样处理。→ 验证方式：装完在后台点一次「保存全部设置」，看 `config.json` 有没有落盘、日志有没有权限错。
3. **升级 / 卸载到底会不会清理 `@appdata/<app>`？**
   官方只承诺 `var` 是「**应用重启后**保留的运行数据」，**没有承诺升级/卸载不删**；卸载页还让应用自己问用户「保留还是删除数据」。→ 这条决定 v1.3.2 那套「程序自己写快照 + 启动时捡回来」能不能拆。
   **结论先摆出来：不能拆。** 只要官方没承诺，自备份就必须留着——它是补救，`TRIM_PKGVAR` 才是根治。两者并存不冲突（备份放在 `TRIM_PKGVAR/backup` 下）。

## 四、建议的改动范围

### 第一批（v1.5.0）：只改落点与可观测性，不动 Go 代码

| 改动 | 文件 | 代价 / 风险 |
|---|---|---|
| 挂载源改 `${TRIM_PKGVAR}/data` 与 `${TRIM_PKGVAR}/backup` | `app/docker/docker-compose.yaml` | 风险：挂载源不存在时 docker 会建空目录（root 属主），所以 `install_init` 里仍要 `mkdir -p` 两个子目录 |
| 删掉 `detect_volume_root` / `ensure_data_root` / `ensure_backup_root` → 换成一条 `mkdir -p "${TRIM_PKGVAR}/data" "${TRIM_PKGVAR}/backup"` + 老数据迁移 | `cmd/main`（约 250 行可缩到 40 行） | 收益大：三个版本的自造逻辑全拆掉，回到官方机制上 |
| 老路径数据迁移：`share/<app>/data`、`/var/apps/<app>-data` 里的文件搬进 `TRIM_PKGVAR/data` | `cmd/main` 的 `init` | 必须做，否则升级后配置「看起来又丢了」 |
| 所有失败分支不再 `2>/dev/null`，改打日志 + 写 `location-status.txt` | `cmd/main`、`cmd/upgrade_init`、`cmd/install_callback` | 纯增益 |
| `config/resource` 去掉 `data-share` | `config/resource` | 代价：文件管理器里不再出现 `cf-ddns-sidecar` 共享文件夹（那本来就是「不该暴露的内部数据」） |
| `manifest` 补 `os_min_version`、`changelog` | `manifest` | 需要你告诉我真机飞牛版本号 |

**验证方式（你照这个点）**：装完打开「应用中心 → 本应用 → 运行日志」，第一屏应该出现类似「数据目录：/app/data（TRIM_PKGVAR=…）」「备份目录可用：共 N 份」；然后后台点「保存全部设置」，再点「立即测速」跑一次，最后去文件管理器看「存储空间1 → @appdata → cf-ddns-sidecar」里是否有 `data` 与 `backup` 两个文件夹。

### 第二批（以后）：不着急，等第一批稳了再说

- `run-as: root`：如果第一批选了官方路径且 ACL 生效，就**不需要**动权限（比官方标准还更保守）。
- `etc`/`var` 拆分、`disable_authorization_path`、`platform=all`、`wizard/uninstall` 让用户选是否留数据。
- 补 `os_max_version`。
