# 备份目录搬迁方案（v1.6.3 候选）

> 起因：`docs/官方规范对账.md` 的 **A2** —— 官方没有「独立备份目录」这个概念，
> 建议备份放在 `${TRIM_PKGVAR}/backup`；我们仍在 `/var/apps/cf-ddns-sidecar-backup`。
> 本文只出方案，**不改代码**。

> **已定：选甲（2026-11-18）** —— 搬到 `${TRIM_PKGVAR}/backup`。
> 已确认并接受这条代价：备份从「应用目录的兄弟」变成「数据目录内部」，
> 卸载时与数据同归于尽。v1.6.3 实现。

---

## 一、结论先说

读完代码后发现一件事，它把这件事的性质变了：

**搬到官方建议的位置，会让备份和数据同生共死。**

现在的 `/var/apps/cf-ddns-sidecar-backup` 是应用目录的**兄弟**：
`uninstall_callback` 完全不碰它（我逐行看过，脚本里连 "backup" 这个词都没有），
所以它能活过卸载、活过「平台删掉整个 `/var/apps/<app>`」。

而官方建议的 `${TRIM_PKGVAR}/backup` 在**数据目录里面**。数据没了，备份跟着没。

所以这不是「挪个位置让它更规范」，而是**拿一层保险换一条合规**。三个方案见第三节。

---

## 二、现在到底怎么跑的（事实，逐条核过）

| 角色 | 位置 | 它认的路径 | 在真机上实际做什么 |
|---|---|---|---|
| 容器挂载 | `docker-compose.yaml:91` | `/var/apps/cf-ddns-sidecar-backup:/app/backup` | 把宿主目录挂进容器 |
| 容器入口（root） | `docker-entrypoint.sh:24,63-72` | `CFDDNS_BACKUP_DIR` 或 `/app/backup` | `mkdir -p` + `chown -R app:app`，失败退 `chmod 0777` |
| Go 程序 | `config/backup.go`、`config/restore.go:57` | `CFDDNS_BACKUP_DIR` 或 `/app/backup` | 每次保存配置后写一份快照，只留 3 份，内容没变不重复备 |
| 宿主机脚本 | `cmd/main:412-430` | 硬编码 `/var/apps/${APP_NAME}-backup` | `mkdir -p` + `chown 1000:1000`。**`TRIM_PKGVAR` 存在时只建目录，不搬卷** |
| 宿主机脚本 | `cmd/upgrade_init:49-51` | 同一个路径，先 `readlink -f` 解析 | 升级前备一份，留 3 份，写不进去就退到两级更差的位置 |
| 宿主机脚本 | `cmd/uninstall_callback` | **完全不提备份** | 什么都不做 → 这就是它能活过卸载的原因 |

真机现状（2026-11-18 08:56 日志）：`备份目录 /app/backup 可用：共 3 份，最新 20261118-083306`。

### 顺带查出一段死代码

`cmd/main` 里的 `ensure_backup_root()`（161-226 行，约 65 行）和 `detect_volume_root()`
里只服务它的那半段，**在真机上永远走不到**——它们只在 `TRIM_PKGVAR` 为空时才被调用，
而真机上它是有值的（v1.5.0 探针已证明）。那套「搬到 `/vol1/<app>-backup` 再建软链」的
逻辑，以及它那些「备份目录已搬到存储卷」的日志分支，现在全是不会执行的代码。

这件事本身值得处理：一段永不执行的代码留在那儿，以后排查时无法从代码判断
「日志里没这句话，是没搬到还是没走到」。

## 三、三个方案

### 甲、官方位置：`${TRIM_PKGVAR}/backup`

真机上就是 `/vol1/@appdata/cf-ddns-sidecar/backup`。

- 合规：✅ 与官方建议一致
- 安全：❌ 备份进数据目录
- **关键副作用**：数据挂载的是整个 `${TRIM_PKGVAR}`，所以备份会以
  `/app/data/backup` 的形式出现在数据目录内部。后果：
  1. 「数据目录被清空」时备份一起没——虽然升级不删 `@appdata`（实测两次），
     但卸载大概率会删；
  2. 与 2026-11-17 那条教训「**备份不能放在会被删的那层里**」方向相反。
- 好处：少一个挂载点、少一套 chown、路径不用猜
- 改动量：compose 1 行 + `cmd/main` 1 行 + `upgrade_init` 1 行 + 入口脚本加搬迁段

### 乙、`@appdata` 下的兄弟目录：`/vol1/@appdata/cf-ddns-sidecar-backup`

- 合规：🟡 仍是自造目录，但挪进了平台管的目录树，不在数据目录里
- 安全：✅ 与现在等同（活过 `/var/apps/<app>` 整层删除，也活过数据目录被清）
- 代价：compose 里要写成 `${TRIM_PKGVAR}/../cf-ddns-sidecar-backup`，
  **依赖 docker 把 `..` 规范化**。这一点本机验不了（本机没有飞牛，
  `TRIM_PKGVAR` 是空的）。万一没规范化，会建出一个字面名叫 `..` 的目录——
  这种故障很难从日志看出来。
- 改动量：同甲

### 丙、不搬，只清死代码，把 A2 记为已知偏离

- 合规：❌ 继续挂账（若将来上架应用中心，审查会点出来）
- 安全：✅ 维持现状
- 风险：**0**（不动任何运行路径）
- 做的事：
  1. 删掉 `ensure_backup_root()` 和 `detect_volume_root()` 里只服务它的那半段，
     连带那些永不打印的日志分支；
  2. 在 `docs/官方规范对账.md` 的 A2 写明「**刻意不搬**：备份要活过卸载，
     官方建议的位置在数据目录内，卸载时会同归于尽」；
  3. 顺带把 `cmd/main` 里「探针期间备份位置刻意不动」那句注释更新成正式决定。
- 收益：少 60 多行永不执行的代码；以后排查不用再猜那段是死是活

## 四、如果选甲或乙，还得解决「旧备份怎么办」

切了挂载源，新目录是空的，老目录那 3 份会变成孤儿。程序启动会显示
「备份目录可用，目前是空的」——**不是丢数据**（`config.json` 还在数据目录里），
但下一次升级的窗口里没有安全网。

做法照搬数据迁移那一套（`/app/legacy-data:ro` 的现成模式）：

1. compose 里把老目录**只读**挂成 `/app/legacy-backup:ro`；
2. 容器入口（root 身份）发现「`/app/backup` 里没有快照、`/app/legacy-backup` 里有」→
   `cp -a` 过来，再 `chown -R app:app`；
3. **老目录不删**，留作回退点（和旧数据目录同一个原则）。

---

## 五、怎么验证

**本机能验的**（用 docker 造假目录）：
- 入口脚本在「新目录空 + 老目录有 3 份」时把 3 份搬过去，属主变 `app:app`；
- 新目录已经有快照时不重复搬、不覆盖；
- 老目录只读挂载时，搬迁不会试图删它。

**本机验不了的（必须真机）**：
- `${TRIM_PKGVAR}/../` 会不会被 docker 规范化（只有乙涉及）；
- 覆盖升级后老备份还在不在、新位置有没有被平台动过。

所以至少装两次：第一次证明「搬过去了」，第二次证明「升级之后它还在」。

## 六、最终决定：选甲（已实施）

> **v1.6.5 归档说明**：本节原来叫「我的建议：选丙」，是我在讨论阶段的倾向。
> 你后来选了**甲**，v1.6.3 已实施并真机验收通过，所以那一节的建议**已作废**，
> 换成下面这段结论。保留这份文档是为了留住「三个方案怎么比较出来的」，
> 但**不要再按它做决策**。

当时不选甲的理由是「搬迁把合规换成了安全」：官方那条建议的前提是「`var` 是
平台管的持久目录，放里面不会丢」——这个前提对**升级**成立（实测两次，
`@appdata` 一直在），对**卸载**不成立。

你确认接受了这条代价，换来的是符合官方布局、少一层自造目录。现状：

- 备份在 `${TRIM_PKGVAR}/backup`，真机是 `/vol1/@appdata/cf-ddns-sidecar/backup`
- 容器内仍是 `/app/backup`，程序读写路径一行没改
- v1.6.2 及更早的备份在 `/var/apps/<app>-backup`，由容器入口只读挂载后自动搬
- **卸载时数据和备份会一起没**（这是选甲时就确认的）

如果以后真要上架应用中心、且需要保住「备份能活过卸载」，那时再考虑**乙**。
